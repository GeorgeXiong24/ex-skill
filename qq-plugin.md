# Connecting an imitation skill to QQ

This guide describes how to combine skills generated by this repository with
[qq-bridge](https://github.com/Derpyu520/qq-bridge), [SnowLuma](https://github.com/SnowLuma/SnowLuma), and
DeepSeek Harness (DSH), so messages received by a QQ account can be answered by a DSH agent using a selected persona.

> **Integration note:** an imitation skill is a directory containing a `SKILL.md` and a profile file; the qq-bridge
> console manages persona/role prompts. The upstream documentation does not describe uploading or importing an entire
> skill directory through the console. Do not treat copying the whole directory into the console as a required step.
> Instead, adapt the generated skill into a persona prompt in the console, and keep the original skill directory locally
> as the source artifact.

## Components and message flow

```text
chat logs / documents / images
        │
        ▼
personality-analysis-skill ──► personality profile .md
        │
        ▼
imitation-skill-generator ──► skills/imitation-<alias>/
        │                       ├── SKILL.md
        │                       └── references/<alias>_personality_profile.md
        ▼
adapt the skill into a persona prompt ──► qq-bridge console: “Personas & Roles”
                                                    │
QQ client ◄── OneBot ◄── SnowLuma ◄── qq-bridge ◄──► DeepSeek Harness
```

- **ex-skill** analyzes materials locally and generates a profile and imitation skill.
- **SnowLuma** connects to the QQ client and exposes a OneBot interface; you install, log in to, and start it yourself.
- **DeepSeek Harness** runs the DSH agent and model.
- **qq-bridge** connects QQ/OneBot messages to DSH; its local console manages runtime mode, allowlists, and persona prompts.

## Prerequisites

1. **DeepSeek Harness:** install and start DSH on the machine that will run the bridge, and make sure its local Web
   address is reachable. The current qq-bridge README uses `http://127.0.0.1:3080` as an example; use your actual
   configured address if it differs.
2. **SnowLuma:** obtain a release for your environment from
   [SnowLuma Releases](https://github.com/SnowLuma/SnowLuma/releases), then follow SnowLuma's instructions to install,
   start, log in to QQ, and complete its WebUI setup. The default SnowLuma WebUI address is typically
   `http://localhost:5099`; use the address shown in its startup log.
3. **Skills from this repository:** load `skills/personality-analysis-skill/` and
   `skills/imitation-skill-generator/` in an agent environment that supports these skills. See
   [Usage in the README](./README.md#usage) for the local generation workflow.
4. Use only materials you are authorized to process, and obtain appropriate consent before imitating a real person.
   Chat logs, profiles, and generated outputs may contain sensitive information.

## Procedure

### 1. Analyze materials and generate the imitation skill

1. Provide chat logs, documents, or images to `personality-analysis-skill`. Identify which speaker is the subject, and
   ask it to produce a `<subject>_personality_profile.md` following the profile template.
2. Review the subject, language, traits, tone, memories, and confidence in the profile. Preserve uncertainty when the
   evidence is insufficient; do not present guesses as facts.
3. Give the profile to `imitation-skill-generator` to create `skills/imitation-<alias>/`.
4. Confirm that the output includes `SKILL.md` and
   `references/<alias>_personality_profile.md`. Test the generated skill locally with several prompts before using it
   through QQ.

### 2. Install and configure qq-bridge

Follow the latest instructions in the [qq-bridge README](https://github.com/Derpyu520/qq-bridge). These are the typical
steps listed by its README; use the upstream docs and configuration template if they change:

```bash
git clone https://github.com/Derpyu520/qq-bridge.git
cd qq-bridge
npm install
cp config.example.json config.json
```

On Windows CMD, use `copy config.example.json config.json` instead of `cp`.

Edit the local `config.json` and check at least these settings:

- `dsh.baseUrl`: local DSH address; the example default is `http://127.0.0.1:3080`.
- `snowluma.wsUrl`: SnowLuma OneBot WebSocket address, for example `ws://127.0.0.1:3001`.
- `snowluma.httpUrl`: SnowLuma OneBot HTTP API address, for example `http://127.0.0.1:3000`. Do not use the WebSocket port here.
- `snowluma.accessToken`: enter the SnowLuma **HTTP API** access token; leave it blank if no token is configured. SnowLuma's HTTP and WebSocket tokens may differ, and the bridge attempts to discover the WebSocket token automatically.
- `snowluma.homeDir`: the extracted/installed SnowLuma directory. The bridge uses it to discover the account's OneBot configuration and WebSocket token; set the actual directory if discovery fails.
- `allow.private`: the **friend QQ IDs** allowed to trigger the bot; `allow.groups`: the **QQ group IDs** allowed to trigger it. These are the sender/group IDs, not the bot account's own QQ ID.
- `deny.private` / `deny.groups`: deny lists; a matching user or group is blocked even if also present in an allowlist.
- `allowAllWhenEmpty`: keep this `false`. When both allowlists are empty, messages are ignored by default; setting it to `true` opens all private/group chats when the lists are empty and is high risk.
- `consolePort` / `consoleToken`: local console port and access token. With the default port, the console is at
  `http://127.0.0.1:3100`. Treat the token as a credential; do not publish it or commit it.

Here is an **example fragment**. Replace the placeholder strings with your own numeric IDs. It shows where the settings go; do not
paste it as a second top-level JSON object into an existing file, and do not add comments to JSON:

```json
{
  "snowluma": {
    "wsUrl": "ws://127.0.0.1:3001",
    "httpUrl": "http://127.0.0.1:3000",
    "accessToken": "your SnowLuma HTTP API token",
    "homeDir": "/path/to/your/SnowLuma/install"
  },
  "allow": {
    "private": ["REPLACE_WITH_ALLOWED_FRIEND_QQ_ID"],
    "groups": ["REPLACE_WITH_ALLOWED_GROUP_ID"]
  },
  "deny": {
    "private": [],
    "groups": []
  },
  "allowAllWhenEmpty": false,
  "ownerQQ": "REPLACE_WITH_ADMIN_QQ_ID",
  "consolePort": 3100,
  "consoleToken": ""
}
```

Replace the placeholder strings with the friend QQ IDs and group IDs you allow; `ownerQQ` is only needed for
`closed-agent` mode. IDs are written as strings, and the bridge normalizes IDs to strings for comparisons. JSON numbers
are also accepted. Use the actual ports
and token configured in the SnowLuma WebUI. The default
HTTP API port is usually `3000` and the WebSocket server port `3001`; HTTP and WebSocket tokens for the same account may
differ. Put the HTTP token in `snowluma.accessToken`. A first WebSocket `1006` followed by automatic recovery and a
connected message may be normal token recovery; repeated recovery failure means you should check `homeDir` and the
SnowLuma account that is logged in.

### Where to manage the allowlist

You can edit `allow.private`, `allow.groups`, and `deny.*` directly in `config.json`, or manage the allowlist in the
running qq-bridge console under **“Access & Security”**. Confirm that console changes are saved; restart qq-bridge after
editing `config.json`. The allowlist also limits the destinations that the bridge's agent-facing send-message tools may
target.

To use `closed-agent` (admin-only private chat), also set `ownerQQ` in `config.json` to the administrator's QQ ID. It
serves a different purpose and does not automatically replace the allowlist, so also add the administrator's QQ ID to
`allow.private`. In ordinary `chat` mode, configure the allowed friends/groups using the allowlist.

### 3. Install the qq-bridge DSH presets and MCP servers

From the `qq-bridge` repository directory, run:

```bash
node scripts/setup-dsh.mjs
```

This configures the `qq-chat` / `qq-chat-v2` presets and MCP servers used by the bridge. Restart DSH after setup so it
loads the configuration. This is a required integration step, even if the bridge process itself starts successfully.

### 4. Start SnowLuma and qq-bridge

1. **Start SnowLuma:** open the downloaded and extracted release directory. On Windows, run `launcher.bat`; on Linux,
   run `launcher.sh` (first use `chmod +x launcher.sh` if needed). For other operating systems, follow the instructions
   included with that release; the current upstream README explicitly lists Windows and Linux launch commands. Do not
   start SnowLuma from this repository or have the bridge install/start it for you. After logging in to QQ through the SnowLuma WebUI, open its OneBot configuration
   and enable both the **WebSocket server** and **HTTP API**; note their ports and access tokens. The initial SnowLuma
   WebUI password is printed in SnowLuma's startup log; follow its first-run flow to set your own password. This is the
   **SnowLuma WebUI password**, not the qq-bridge console token.
2. **Start DSH:** start the DeepSeek Harness service/application using its own installation method and confirm the local
   address configured as `dsh.baseUrl` is reachable (example: `http://127.0.0.1:3080`). DSH is not started by `npm start`.
3. **Start qq-bridge:** from the root of the `qq-bridge` repository, run:

   ```bash
   npm start
   ```

   This command runs `node src/bridge.js`; on Windows, the upstream docs also provide `start.bat` for supervised startup.
   `npm start` is a foreground process, so closing the terminal stops the bridge.
4. Confirm the logs show a SnowLuma connection. If it keeps failing, check the OneBot WebSocket and HTTP URLs, HTTP token,
   SnowLuma login state, and that `snowluma.homeDir` points to the installation currently running.
5. Open the local qq-bridge console at `http://127.0.0.1:3100` (or `http://localhost:3100`).
   - The login key is the **qq-bridge console token**, not the QQ password, SnowLuma WebUI password, or DSH password.
   - If `consoleToken` in `config.json` is non-empty, use that value.
   - If `consoleToken` is empty, the bridge generates a token on first startup and prints it in the qq-bridge startup
     log. It also saves it to `qq-bridge/state/console-token`; if you missed the log, read that file locally. Do not
     share the token.
   - You can change/regenerate the console token in **“Access & Security”**. If you forget it, stop the bridge and
     set `consoleToken` in `config.json` to a new explicit value, then restart. Setting it to an empty string does not
     clear a token already saved in `state/console-token`; do not delete the whole `state/` directory.

> For JSON paths on macOS/Windows, prefer forward slashes (for example `C:/SnowLuma`). If you use Windows backslashes,
> escape them in JSON (for example `C:\\SnowLuma`) or parsing may fail.

### 5. Create an imitation persona in qq-bridge

1. In the console, open **“Personas & Roles”** and create a role. Use an alias rather than a real name where possible.
2. Open `skills/imitation-<alias>/SKILL.md` locally and refer to
   `references/<alias>_personality_profile.md` in the same directory.
3. Adapt content suitable for persistent conversation guidance into a **persona prompt**, then enter it in the new role.
   Useful details include:
   - evidence-supported background, core traits, and emotional/expressive patterns;
   - language features such as tone, sentence length, vocabulary, emoji use, and reply rhythm;
   - key memories that are documented in the profile and needed for the intended conversations;
   - an instruction not to invent experiences, relationships, or facts when uncertain.
4. Do not paste frontmatter, skill-framework instructions, relative file paths, or unrelated tool-use steps verbatim.
   A console persona prompt is not the same format as a skill directory; transfer the necessary persona information as
   text. Include only the minimum personal information needed at runtime.
5. Save and select/activate the role in the console. qq-bridge combines role prompts with session presets such as
   `qq-chat` or `qq-chat-v2`; do not remove or overwrite preset rules for message handling, tool boundaries, or safety.

If you want DSH to use the complete generated directory as a skill in other contexts, install/load it through DSH's own
supported skill mechanism. That is separate from configuring a role prompt in the qq-bridge console.

### 6. Set the response scope and test end to end

1. Make sure `allow.private` / `allow.groups` contain only the test account or group. Deny rules in `deny.*` take precedence.
2. Select an appropriate runtime mode in the qq-bridge console. For ordinary allowlisted chat, start with the upstream
   `chat` mode. Configure `reserved` / `reserved2` only if you want their simulation behavior and have followed the
   corresponding qq-bridge instructions. Do not enable unrestricted access just to make every group trigger the bot.
3. Send a normal message from an allowlisted test account and verify that:
   - qq-bridge logs the incoming message and delivers it to DSH;
   - DSH uses the intended chat preset and active persona to generate a reply;
   - SnowLuma sends the reply back to QQ.
4. Test a few more message types, and verify that an account or group outside the allowlist does not trigger a reply.
   Adjust the persona prompt and test again if the style needs tuning.

## Troubleshooting

| Symptom | Checks |
| --- | --- |
| No reply in QQ | Is DSH running? Did you run `node scripts/setup-dsh.mjs` and restart DSH? Do bridge logs show a SnowLuma connection? Is the sender/group allowlisted, and is the runtime mode correct? |
| SnowLuma is connected, but DSH creates no session or reply | Check `dsh.baseUrl`, DSH availability, and bridge logs. Confirm DSH loaded the qq-chat preset and MCP servers. |
| SnowLuma cannot connect or token recovery keeps failing | Check that `wsUrl` and `httpUrl` point to the WebSocket and HTTP ports respectively; `accessToken` should be the HTTP token. Check that `homeDir` points to the actual SnowLuma installation. Different HTTP/WS tokens can be normal. |
| MCP HTTP actions fail | Check that `snowluma.httpUrl` points to the HTTP API port, not the WebSocket port, and verify the HTTP token. |
| Console opens but login fails | Check `consoleToken` in `config.json`; if it is empty, get the token from the startup log or `state/console-token`. It is separate from the SnowLuma WebUI initial password. |
| Console is unavailable | Confirm the bridge is running and check `consolePort`; the default address is `http://127.0.0.1:3100`. |
| The generated skill has no effect on QQ replies | Adapt the required profile information into a console role and save/activate it. Generating a skill locally does not automatically load it into qq-bridge. |

## Privacy and security

- The skills do not themselves publish or upload source evidence, profiles, or generated skills. However, the AI runtime
  may send prompts and supplied content to its configured model provider; check the DSH/model provider's data-handling
  terms and configuration. If the content must not leave your device, use a suitable local model and runtime.
- Do not commit source evidence, profiles, or generated skills to a public repository, paste them into public issues, or
  upload them to untrusted services.
- Treat `config.json`, access tokens, QQ/group IDs, and persona prompts containing private conversations or memories as
  sensitive.
- Do not expose the local console to the public Internet or untrusted networks, and never publish its access token.
- Validate the setup with a minimal allowlist. Expanding the allowlist sends more users' messages to the model.
- Imitate a real person only with appropriate consent; do not present AI replies as if they were sent by that person.
